# ADR-004: Compilação assíncrona via RabbitMQ, com um worker por fila

## Status
Accepted (2026-10-30)

## Contexto
Compilar (`gcc`) e gerar assembly (`gcc -S`) leva de dezenas de ms a vários segundos, consome CPU e roda código enviado pelo usuário. Se feito dentro da requisição HTTP:
- a requisição fica presa enquanto o gcc roda, e um pico de builds esgota o source-service, derrubando também a leitura de arquivos;
- um crash do compilador derruba o serviço de negócio.

## Alternativas consideradas
1. **Compilar dentro do source-service, de forma síncrona**: mais simples, mas acopla CPU de build à latência de leitura.
2. **Worker chamado por HTTP (`POST /compile`)**: isola o processo, mas continua síncrono e sem fila para absorver picos.
3. **Kafka**: log persistente e replay, porém pesado demais para filas de trabalho simples.
4. **RabbitMQ com o padrão Queue**: filas duráveis, entrega a um consumidor por vez, ack/nack e dead-letter.

## Decisão
O source-service grava o build como `pendente`, publica `{build_id, source_id, name, version, kind, correlation_id}` na fila `compila` ou `assembla` (mensagem persistente, publisher confirms) e responde **202 Accepted**. Workers dedicados (`compila-worker`, `assembla-worker`, configurados por `WORKER_QUEUES`) consomem com `prefetch 1`, buscam a fonte, rodam o gcc, gravam o artefato no blob-service e devolvem o resultado por `PUT /builds/:id`. Falhas inesperadas vão para a DLQ `builds.dlq`.

## Consequências

Positivas:
- Picos de build ficam na fila em vez de derrubar o sistema; a leitura de arquivos não sente a carga de CPU.
- Escala horizontal trivial: `--scale compila-worker=3` (com 2 workers, 8 builds foram divididos em 5/3).
- Cada tipo de build escala de forma independente.
- Se o RabbitMQ cair, o pedido é marcado como erro com uma explicação clara e o resto do sistema continua (o `/health/ready` do source fica `degraded`).

Negativas / Trade-offs:
- Consistência eventual: o usuário vê "na fila…" e a tela consulta o status a cada 1 s.
- Mais um componente para operar (RabbitMQ) e a necessidade de manter a declaração das filas idêntica nos dois lados (senão `PRECONDITION_FAILED`).

Riscos:
- Entrega "pelo menos uma vez": uma mensagem pode ser reprocessada se o worker cair depois do gcc e antes do ack. Mitigação: o resultado é idempotente (o `PUT` sobrescreve o mesmo build).
- A DLQ cresce sem ninguém olhar. Mitigação: alerta no Grafana para logs "enviado para a DLQ" (proposto).
