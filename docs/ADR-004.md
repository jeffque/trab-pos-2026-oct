# ADR-004: Compilação por arquivo, assíncrona via RabbitMQ, com resultado via HTTP

## Status
Accepted em 2026-10-30; Superseded by [ADR-011](ADR-011.md) em 2026-10-30

## Contexto
Compilar com `gcc` leva de dezenas de ms a vários segundos, consome CPU e roda código enviado pelo usuário. Feito dentro da requisição HTTP, um pico de compilações esgotaria o source-service e derrubaria também a leitura de arquivos. Na primeira implementação, interpretamos as operações do diagrama como:
- **compila**: um único arquivo `.c` → executável;
- **assembla**: um único arquivo `.c` → listagem em assembly (`gcc -S`).

## Alternativas consideradas
1. **Compilar dentro do source-service, de forma síncrona**: acopla CPU de build à latência de leitura.
2. **Worker chamado por HTTP**: isola o processo, mas continua síncrono e sem fila para absorver picos.
3. **Kafka**: log persistente e replay, pesado demais para filas de trabalho.
4. **RabbitMQ (padrão Queue)**, com o worker devolvendo o resultado por `PUT /builds/:id` no source-service.

## Decisão
O source-service gravava um "build" `pendente` por revisão de arquivo, publicava na fila `compila` ou `assembla` e respondia 202; workers dedicados rodavam o gcc e devolviam o resultado por **HTTP** ao source-service.

## Consequências

Positivas:
- Validou a infraestrutura assíncrona: filas duráveis, publisher confirms, `prefetch 1`, DLQ, workers escaláveis, Correlation ID atravessando a fila.

Negativas / Trade-offs:
- **Divergia do domínio proposto pelo criador do projeto**: não havia workspace (conjunto de fontes), `.h` não podiam ser incluídos entre arquivos, não havia arquivo objeto, e "assemblar" significava gerar assembly em vez de linkar objetos num executável.
- O worker conhecia o endpoint HTTP do dono do pedido (acoplamento) e o source-service acumulava responsabilidades de build.

Riscos (que se confirmaram):
- Ao comparar com a descrição original da ideia, o fluxo de build foi refeito: ver ADR-011. A infraestrutura de fila e de workers foi mantida.
