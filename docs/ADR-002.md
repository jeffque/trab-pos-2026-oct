# ADR-002: BFF com renderização no servidor (Express + Liquid + HTMX)

## Status
Accepted (2026-10-29)

## Contexto
A interface precisa listar arquivos, editar código, navegar entre revisões e acompanhar builds. O navegador não deve conhecer a topologia interna (source, blob, filas) nem o `blob_id`. O grupo é pequeno e o foco da disciplina é o back-end distribuído, não um front-end complexo.

## Alternativas consideradas
1. **SPA (React/Vue) chamando os serviços direto**: expõe a topologia interna ao navegador, exige CORS e um build de front separado.
2. **SPA + API Gateway**: resolve a exposição, mas soma dois componentes e mais código no cliente.
3. **BFF (Backend for Frontend) renderizando HTML no servidor, com HTMX** para trocar só partes da página.

## Decisão
Usaremos um BFF em Express que renderiza templates Liquid e usa HTMX (`hx-boost`, `HX-Location`, polling) para navegar sem recarregar a página. O navegador envia formulários url-encoded; o BFF fala JSON com o source-service, através do `source-lb`.

## Consequências

Positivas:
- A topologia interna e o `blob_id` ficam escondidos; o BFF é o único ponto de entrada da interface.
- Pouquíssimo JavaScript no cliente; funciona até sem JS (formulários e links normais).
- O BFF é o lugar natural para criar o Correlation ID (ADR-009) e, no futuro, a sessão/autenticação.

Negativas / Trade-offs:
- Toda interação passa pelo servidor: mais requisições do que uma SPA com estado local.
- O acompanhamento de build usa polling a cada 1 s, o que gera tráfego enquanto há pedido na fila.

Riscos:
- O BFF vira ponto único de falha da interface. Mitigação: ele é stateless e pode ganhar réplicas atrás de um LB como os demais.
