# ADR-009: Logs JSON com Correlation ID, centralizados em Loki e Grafana

## Status
Accepted (2026-10-30)

## Contexto
Um clique em "Compilar workspace" passa por BFF → workspace-service → RabbitMQ → compila-worker → source-lb → source-service (uma de 2 réplicas) → blob-lb → blob-service (uma de 2 réplicas) → RabbitMQ (evento) → workspace-service. Com `console.log` solto em cada serviço e `docker compose logs` separado por container, era impossível reconstruir o caminho de um pedido ou descobrir em qual réplica um erro aconteceu. O plano da disciplina exige log estruturado com Correlation ID e health check.

## Alternativas consideradas
1. **Só log JSON + Correlation ID**, consultado com `docker compose logs | grep`: cumpre o mínimo, mas não há busca centralizada.
2. **Dozzle**: visualizador web leve, sem busca estruturada nem agregação.
3. **ELK / OpenSearch**: completo, mas pesado (vários GB de RAM).
4. **OpenTelemetry + Jaeger/Tempo (tracing)**: o ideal para latência por etapa, porém com muito mais instrumentação.
5. **pino (JSON) + Correlation ID + Alloy → Loki → Grafana**.

## Decisão
- Todos os serviços usam **pino** (uma linha JSON por evento: `time`, `level`, `service`, `instance`, `msg`, `correlation_id`...). Os nginx também logam em JSON com o Correlation ID.
- O **Correlation ID** nasce no BFF (ou vem do header `X-Correlation-ID`), fica em `AsyncLocalStorage` durante a requisição, é propagado por header HTTP e **dentro da mensagem do RabbitMQ**, e é gravado em cada workspace e assemblagem.
- O **Alloy** lê o stdout dos containers do projeto, o **Loki** guarda e o **Grafana** (porta 3003) traz o dashboard "Logs" com filtro por Correlation ID e por serviço.
- **Health checks** `/health/live` e `/health/ready` em todos os serviços, usados pelo compose, distinguindo dependência crítica (503) de não crítica (200 `degraded`).

## Consequências

Positivas:
- Um pedido é rastreado de ponta a ponta com uma busca, inclusive através da fila e do evento de volta; a interface leva direto ao Grafana filtrado (link "logs" na compilação/assemblagem e Correlation ID no carimbo).
- Achou bugs reais: todo `PUT /builds` respondia 500 (uma variável escondia a função de log) e o processo que morria quando o banco reiniciava.
- Mudar de ferramenta (ex.: Elastic) não exige mexer nos serviços: eles só escrevem JSON no stdout.

Negativas / Trade-offs:
- Mais três containers (Loki, Alloy, Grafana).
- Logs dão o "o quê" e o "onde", mas não o tempo gasto em cada etapa com precisão (isso seria tracing).

Riscos:
- O Alloy lê o `docker.sock` (somente leitura) e o Grafana está com acesso anônimo de admin: aceitável só no ambiente local. Em produção, usar driver de log do Docker e login no Grafana.
- Logs ficam em memória (tmpfs) e somem no `down`; em produção, armazenamento persistente e retenção definida.
