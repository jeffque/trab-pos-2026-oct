# ADR-007: Réplicas atrás de load balancer nginx

## Status
Accepted (2026-10-30)

## Contexto
Com uma instância por serviço, qualquer queda ou deploy derruba a funcionalidade, e a capacidade de leitura fica limitada a um processo Node. O diagrama do grupo previa LB na frente do source-service e do blob-service. Os dois serviços são stateless (todo estado está no Postgres).

## Alternativas consideradas
1. **DNS round-robin do Docker** (`deploy.replicas` sem LB): sem configuração extra, mas o cliente Node resolve um IP e não faz failover.
2. **Traefik** com descoberta automática por labels: bom, mas é mais um componente com configuração própria para aprender.
3. **Kubernetes Service**: fora do escopo do ambiente local da disciplina.
4. **nginx** com `upstream ... resolve`, reconsultando o DNS do Docker.

## Decisão
O compose sobe `source-service` e `blob-service` com 2 réplicas cada, sem porta no host. Na frente de cada um há um nginx (`source-lb` na porta 3002, `blob-lb` na 3001) com `server <serviço> resolve` (DNS reconsultado a cada 5 s), round-robin, `proxy_connect_timeout 500ms` e `proxy_next_upstream error timeout http_502`. Todas as chamadas internas usam os LBs. O header `X-Upstream` mostra qual réplica respondeu.

## Consequências

Positivas:
- Tolerância a falha: com uma réplica de cada serviço derrubada, 20 de 20 leituras responderam 200.
- Escala sem reconfigurar nada: `docker compose up -d --scale source-service=4`; réplicas novas entram em até 5 s.
- Base para rolling update: subir a nova versão, esperar o `/health/ready`, retirar a antiga.

Negativas / Trade-offs:
- Mais dois containers e mais um salto de rede por chamada.
- O próprio LB é instância única (ponto único de falha).

Riscos:
- Requisição em andamento numa réplica que cai pode falhar (o nginx não repete POST já enviado). Mitigação: o cliente pode repetir; operações de leitura são repetidas automaticamente.
- O failover é passivo (o nginx descobre a falha na próxima tentativa), não há health check ativo no nginx open source.
